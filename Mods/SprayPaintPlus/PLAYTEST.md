# Spray Paint Plus Playtests

Implemented changes awaiting in-game confirmation. An agent records a playtest here, not in `TODO.md`, when it has changed code whose behavior can only be confirmed by running the game: single-player, a hosted multiplayer session, or the dedicated server under `DedicatedServer/`. This keeps `TODO.md` a list of work still to do, and gives one place to check whether a change already has a pending test before adding another.

Rules:
- Add an entry when code is implemented but its in-game behavior is unconfirmed. Write down everything a tester needs: what changed (commit if there is one), single-player vs multiplayer / dedicated-server, the save or world to set up, the exact in-game steps, what to watch (InspectorPlus request files, specific log lines, on-screen behavior, IC10 reads), and the expected result. Point at any staged `.work/<date>-<slug>/` request files or playbook.
- Check first. Before adding, scan the entries below so a change already covered by a pending test is not duplicated; extend the existing entry instead.
- Remove an entry when one of these happens: a run confirms it works; a run shows it broken (then add a fresh `TODO.md` item for the fix, or keep working on it now); or the player says the playtest is done. Entries are plain bullets, not checkboxes: like `TODO.md`, finished items are removed, not ticked off. Outcomes live in git history.

The v1.11.0 paired-settings work is verified headlessly as far as it can be: 111 assertions passed on the dedicated server covering the merge truth table, the cycling ladder in all nine client-by-server combinations, authority resolution in all three network roles, paint-family grouping across the full 16x16 matrix, and the effective-settings log line. Re-run any time with `Scenario = spp-settings-merge-verify` in `install/BepInEx/config/net.scenariorunner.cfg`. The entitlement half re-runs with `spp-dlc-gate-verify`.

What no headless run can reach is the settings panel rendering, the join payload actually crossing the wire, two clients with different preferences, and console messages appearing on screen. The three sessions below cover all of that. They are ordered cheapest first, and each is deliberately loaded so one session settles many assertions at once.

- **Session 1: single-player, about five minutes.** Nothing here needs a second machine. Any save with a pipe run, a painted wall and a spray gun will do.
  - **The dropdown renders with readable labels.** Open the mod settings panel from the main menu (per-mod settings are unreachable once a save is loaded, so it has to be the main menu or the Workshop sidebar). Both `Color Cycling` entries, client and server, must show a dropdown offering `Can cannot change color`, `Cycles within paint family` and `Cycles through all colors`. Seeing `CannotChange` or `WithinFamily` instead means the `[Display]` attributes did not survive. This is the most likely cosmetic failure in the release: it is the repo's first enum-typed setting, so nothing has ever exercised this path before.
  - **Eleven groups, in order.** Confirm the panel shows six `Client - *` groups above five `Server - *` groups, and that entries inside each group follow the order in `README.md` rather than alphabetical.
  - **The three modes behave.** With `Cycles through all colors` the wheel walks every entitled color. With `Cycles within paint family` a base-color can stays on the twelve base colors and a metallic can stays on the four metallic ones, wrapping inside its own family rather than stopping at the edge. With `Can cannot change color` the wheel does nothing and the can keeps whatever color it currently has.
  - **The eyedropper family message.** In `Cycles within paint family`, hold a metallic can and right-click a standard-painted object. Expect a console line naming the reason. Then the reverse, a standard can right-clicking a metallic-painted object. This message is deliberately uncapped, so it must fire on every attempt rather than three times.
  - **Silence is correct here.** Single-player has no server to disagree with, so no join message and no blocked-function warning should appear at all. A warning in solo would mean the merge is misreading `NetworkRole.None`, which is the shape of the v1.2.2 infinite-spray bug.

- **Session 2: listen host plus one joined client, about fifteen minutes.** The load-bearing session. Set both sides deliberately mismatched before starting so a single join settles the whole messaging path.
  - Host: `Server - Color Cycling` = `Cycles within paint family`, `Server - Color Picking` Off, `Server - Network Painting` group with `Network Paint Pipes` Off, `Server - Paintability` Off. Everything else On.
  - Client: everything On, with `Client - Color Cycling` = `Cycles through all colors`.
  - **One consolidated join message.** On joining, the client console must show a single `[SprayPaintPlus]` line naming Color Picking, Network Paint Pipes and Extra Paintable Structures together. Three separate messages means the consolidation is broken. Nothing about Color Cycling, because a stricter server mode is not a blocked function, it simply applies.
  - **The stricter mode applies.** The client asked for all colors and the host said family only, so the client's wheel must stay inside the can's family. This is the join payload proving it crossed the wire. If the client can still reach every color, `SettingsConfigSync` did not land.
  - **First three uses, then silence.** Client right-clicks to eyedrop six times: exactly three warnings naming Color Picking, then nothing. Repeat on a pipe run for Network Paint Pipes, and on a Steel Frame (Corner) for Extra Paintable Structures. The frame case matters most, because before this release it was a completely silent dead click.
  - **Per-player merge with the two of you differing.** Client turns `Client - Network Paint Cables` Off, host leaves the server half On. Client paints a cable: one cable only. Host paints the same run: the whole network floods. That is a client half binding its own owner and nobody else.
  - **Glow, what you can do versus what you see.** Client turns `Client - Glow Paint` Off. Host glow-paints a pipe: the client must still see it glowing. Host then recolors that glowing pipe with a plain can: it must still glow for the client. A pipe that silently stops glowing for one player only is the exact defect the audit found, and this is the most valuable single observation in the session.
  - **The host's own half must not leak.** Host turns `Client - Glow Paint` Off but leaves `Server - Glow Paint` On. The client's gun must keep working normally, and the host sees the result. Before the fix the host's personal setting silently disabled glow for everyone. The host's own gun stays inert, which is what their own half asked for.
  - **Colors survive a remote glow stroke.** Paint a pipe run in three different colors, then have the client glow-paint one pipe of it. Every pipe keeps its own color and only the glow changes. A run that comes back all one color means the index-preserve prefix was skipped.

- **Session 3: dedicated server, about ten minutes, needs one player who owns Metallic Paints and one who does not.** The server under `DedicatedServer/` owns no DLC itself, which is what makes this structurally different from Session 2: a listen host seeds the entitlement pool from its own Steam account, a dedicated server cannot.
  - **Shared DLC across a server that owns nothing.** Once the owning client is fully joined, every connected player must be able to scroll to and paint with metallic colors, including the player who does not own it. That is vanilla shared-DLC behavior, not a bypass. Research resolved from code that the pool is built entirely from what clients report at the very end of their join and is then broadcast back out, but no live session has confirmed it.
  - **Watch for the opposite symptom.** The failure to look for is not a `Rejected ColorIndex` warning; client and server read the same pool, so it should never fire. It is the owning player's wheel skipping the metallic colors despite owning the DLC, which would mean the pool never made the round trip. Check the server log at load for `DLC paint map built: 16 color swatches, 16 spray can prefabs, 4 DLC-gated color(s)`; `0 DLC-gated color(s)` would mean the map latched before the metallic can prefabs registered, leaving every color unrestricted. `dlc shared` prints the live pool and is the fastest diagnostic, though it is host-scoped and so needs `serverrun` from a connected admin client.
  - **The entitlement outlives the owner.** After the owning client disconnects, metallic must stay available to everyone still connected until the world unloads. That is vanilla behavior and worth seeing once.
  - **The notice budget resets with the session.** Server sets `Network Paint Pipes` Off, client leaves its half On, client paints a pipe run repeatedly and gets three warnings. Client disconnects, rejoins, paints again: three fresh warnings. Zero after a rejoin means the per-player prune or the leave-game clear is not firing. While connected, confirm painting is otherwise unaffected and there is no stutter, which would indicate the per-player preference mask being resent every frame.
  - **The mid-session glow notice.** With the client connected and holding a gun, flip `Server - Glow Paint` to Off on the server. The join payload is not resent, so the client still believes glow works and keeps sending strokes. Expect up to three console notices naming Glow Paint, then the gun falling back to vanilla behavior. Strokes aimed at an object already in the requested glow state must produce no notice, because nothing was suppressed there.
