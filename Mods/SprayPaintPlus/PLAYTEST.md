# Spray Paint Plus Playtests

Implemented changes awaiting in-game confirmation. An agent records a playtest here, not in `TODO.md`, when it has changed code whose behavior can only be confirmed by running the game: single-player, a hosted multiplayer session, or the dedicated server under `TestRig/DedicatedServer/`. This keeps `TODO.md` a list of work still to do, and gives one place to check whether a change already has a pending test before adding another.

Rules:
- Add an entry when code is implemented but its in-game behavior is unconfirmed. Write down everything a tester needs: what changed (commit if there is one), single-player vs multiplayer / dedicated-server, the save or world to set up, the exact in-game steps, what to watch (InspectorPlus request files, specific log lines, on-screen behavior, IC10 reads), and the expected result. Point at any staged `.work/<date>-<slug>/` request files or playbook.
- Check first. Before adding, scan the entries below so a change already covered by a pending test is not duplicated; extend the existing entry instead.
- Remove an entry when one of these happens: a run confirms it works; a run shows it broken (then add a fresh `TODO.md` item for the fix, or keep working on it now); or the player says the playtest is done. Entries are plain bullets, not checkboxes: like `TODO.md`, finished items are removed, not ticked off. Outcomes live in git history.

## The 2026-08-12 harness run: seven of eight green

The eight automated checks stood at **7 passed, 1 failed, 0 inconclusive** against game 0.2.6420.27780. Full narrative, per-check detail and every measurement: `.work/2026-08-11-spraypaintplus-playtests/CAMPAIGN-LOG.md`; evidence bundle: `.work/2026-08-12-playtest-spraypaintplus/`.

That run was made with the PowerShell harness. The checks are now C# at `Mods/SprayPaintPlus/playtests/`, compiled into `TestRig/testrig.exe` and run with `testrig playtest` (`--only "<name pattern>"` selects; check names are the `CheckSpec` names, not file names). **The result above has not been reproduced through the ported engine**, and it is against a game version two builds behind the installed 0.2.6428.27798, so re-run before treating any of it as current.

The 2026-08-11 result (0 passed, 2 failed, 6 inconclusive) was **not** evidence against the mod. Every one of those outcomes traced to the harness or to how it read the world, and the three most expensive are worth stating once so nobody re-derives them:

- **`Thing.CustomColor` cannot detect paint.** It is a `ColorSwatch` reference whose rendering is its own type name, so `/thing` reports `matchesPrefab: true` and `isNull: false` on every object in the world, painted or not. Three checks read it and concluded nothing had been painted when every stroke had in fact landed. The readable signal is the row-level `customColorIndex`.
- **A cable spawns at `customColorIndex` 4, which is exactly what `ItemSprayCanRed` applies.** Before and after were identical on a working stroke and on a stroke that never happened. The checks now spawn ColorGray (1) and spray red (4). That also explains the old `baseline-not-matte`: a same-colour repaint never runs `SetCustomColor`, so `EmissionColor` stayed at its `Color.white` initial value.
- **The four `joiner-not-in-roster` results were not join failures.** A `/connect` issued from inside a check body, after that body disconnected the joiner, had its own copy of the bring-up logic and did not confirm-and-retry. That is now one shared `Connect-RigJoiner`.

The mod itself needed no change for any of it.

**Verified by hand on both game builds, before and after the update**: with `Server - Network Painting / Network Paint Cables` off and the client half on, three strokes produce exactly three console notices, the third ending "No more notices about this one until you rejoin.", and a fourth stroke produces silence. The seed always paints (the prefix on `OnServer.SetCustomColor` is `void` and cannot suppress it) and the network flood is correctly withheld.

  What the next attempt needs to know:
  - **`update-game --target server` deletes ScenarioRunner** (it mirrors `BepInEx/` from the client install, which has no server-only dev-plugin) and `deploy` does not put it back. Rebuild `TestRig/DedicatedServer/dev-plugins/ScenarioRunner/ScenarioRunner.sln -c Release`, then `testrig deploy ScenarioRunner --target server --as <id>`. It compiles clean against the new game.
  - **Arm it** with `[Probe] Scenario = spp-settings-merge-verify` in `install/BepInEx/config/net.scenariorunner.cfg`. That file does not exist after a fresh install until the plugin has run once, so it has to be written by hand, and **the session state reset blanks that value at every session boundary**, so arm it after taking the lock and before starting the server.
  - **Prove it armed** before trusting the run: `ScenarioRunner v... loaded; scenario='spp-settings-merge-verify'` must appear in `data/server.log`. `[ScenarioRunner]` output lines land in `install/BepInEx/LogOutput.log`, not in `data/server.log`.
  - **Use `--load <SaveName> --map <Map>`, not `--new`.** The 2026-08-11 attempt spent 17 minutes generating a Lunar world and never reached the dispatcher. `LunaSppTest` and other saves are in `TestRig/DedicatedServer/data/saves/`; stage anything you need to survive BEFORE the session's first mutating command, because a world not in the recorded set is deleted at the session boundary.
  - **The world never ticks with nobody connected.** `GameManager.DelayedStartupPause` parks it about five seconds after start, and measured on 0.2.6428.27798 the tick count stayed at zero for a full 287 s run. A scenario armed at boot then emits one line and nothing else, which looks exactly like a typo in its id. Either connect a client or set `Force Unpause Without Client`.
  - **The 2026-08-12 attempt died on a file-sharing violation**, not on the scenario: `IOException: Sharing violation on path ...\data\setting.xml` followed by `[Global]: An error occurred during loading. Exiting`, after all 62 mods had loaded. Two things held that file at once. Note that `start` reported a healthy pid and `status` afterwards just said `server: stopped`, so an exit during load is indistinguishable from a finished run unless the log is read.
