# Spray Paint Plus Playtests

Implemented changes awaiting in-game confirmation. An agent records a playtest here, not in `TODO.md`, when it has changed code whose behavior can only be confirmed by running the game: single-player, a hosted multiplayer session, or the dedicated server under `DedicatedServer/`. This keeps `TODO.md` a list of work still to do, and gives one place to check whether a change already has a pending test before adding another.

Rules:
- Add an entry when code is implemented but its in-game behavior is unconfirmed. Write down everything a tester needs: what changed (commit if there is one), single-player vs multiplayer / dedicated-server, the save or world to set up, the exact in-game steps, what to watch (InspectorPlus request files, specific log lines, on-screen behavior, IC10 reads), and the expected result. Point at any staged `.work/<date>-<slug>/` request files or playbook.
- Check first. Before adding, scan the entries below so a change already covered by a pending test is not duplicated; extend the existing entry instead.
- Remove an entry when one of these happens: a run confirms it works; a run shows it broken (then add a fresh `TODO.md` item for the fix, or keep working on it now); or the player says the playtest is done. Entries are plain bullets, not checkboxes: like `TODO.md`, finished items are removed, not ticked off. Outcomes live in git history.

- **Metallic Paints DLC gate, in a real client session.** The gate logic itself is already verified headlessly: the `spp-dlc-gate-verify` ScenarioRunner scenario drives `DlcPaintGate` and `ColorCyclerPatch.NextColorInCycle` across four entitlement states (pool empty, pool holding MetallicPaints, owner with the setting off, entitlement withdrawn) and all cases pass, including forward and backward scroll skipping the DLC block and a can escaping a gated color. Re-run it any time with `Scenario = spp-dlc-gate-verify` in `install/BepInEx/config/net.scenariorunner.cfg`. What that run cannot cover is the client-side feel and the multiplayer round trip, so this needs one human pass:
  - **Single-player, DLC not owned.** Hold any spray can, scroll the wheel a full loop in both directions. Expect twelve colors only, no visual stutter or stuck wheel where the metallic block used to be, and the can thumbnail and inventory slot updating on every step. Then right-click (eyedropper) a surface painted obsidian if you can arrange one; expect the can to keep its current color and not pick it up.
  - **Single-player, DLC owned.** Same scroll, expect sixteen colors with the four metallics appearing after Purple. Then set "Enable Metallic Paints" to Off in the mod settings, restart, and expect twelve again while a can that is natively metallic still paints metallic.
  - **Multiplayer, host owns the DLC and the joining client does not.** The shared-DLC pool should let the client scroll to and paint with metallic colors (this is vanilla behavior, not a bypass). Confirm the client sees the correct metallic color on the can and on painted structures, since the sync receive path is deliberately ungated. Watch for `Rejected ColorIndex` warnings in the host log; there should be none from a normal client.
  - **Multiplayer, nobody owns the DLC.** Confirm neither side can reach a metallic color, and that the host log stays free of `Rejected ColorIndex` warnings (a well-behaved client gates itself, so that line firing would mean the client-side gate was bypassed).
