# Spray Paint Plus Playtests

Implemented changes awaiting in-game confirmation. An agent records a playtest here, not in `TODO.md`, when it has changed code whose behavior can only be confirmed by running the game: single-player, a hosted multiplayer session, or the dedicated server under `TestRig/DedicatedServer/`. This keeps `TODO.md` a list of work still to do, and gives one place to check whether a change already has a pending test before adding another.

Rules:
- Add an entry when code is implemented but its in-game behavior is unconfirmed. Write down everything a tester needs: what changed (commit if there is one), single-player vs multiplayer / dedicated-server, the save or world to set up, the exact in-game steps, what to watch (InspectorPlus request files, specific log lines, on-screen behavior, IC10 reads), and the expected result. Point at any staged `.work/<date>-<slug>/` request files or playbook.
- Check first. Before adding, scan the entries below so a change already covered by a pending test is not duplicated; extend the existing entry instead.
- Remove an entry when one of these happens: a run confirms it works; a run shows it broken (then add a fresh `TODO.md` item for the fix, or keep working on it now); or the player says the playtest is done. Entries are plain bullets, not checkboxes: like `TODO.md`, finished items are removed, not ticked off. Outcomes live in git history.

The v1.11.0 paired-settings work is verified headlessly as far as it can be: 104 assertions passed on the dedicated server covering the merge truth table, the cycling ladder in all nine client-by-server combinations, authority resolution in all three network roles, paint-family grouping across the full 16x16 matrix, and the effective-settings log line. Re-run any time with `Scenario = spp-settings-merge-verify` in `install/BepInEx/config/net.scenariorunner.cfg`. The entitlement half re-runs with `spp-dlc-gate-verify`.

Four agent-driven end-to-end runs have happened, all recorded in `.work/2026-07-27-spraypaintplus-settings-split/TEST-RESULTS.md`. The 2026-07-27 run cleared Session 1 entirely and most of Sessions 2 and 3. The 2026-07-28 run cleared most of Session E and the reachable half of Session D against the post-removal build. The 2026-07-29 runs cleared Sessions D and C outright after fixing the two tooling blockers that had stopped the previous run, then closed Session E's last two checks. Read that file's "Notes for a future session" before the next run; the tooling notes in it are the difference between a productive session and a wasted one.

**A driven client can hold an item now.** The ScenarioRunner `give-item` scenario puts any prefab straight into a connected player's hand from the server, which sidesteps the client cursor entirely. Set `Scenario = config-set,give-item` (the string takes a comma-separated list) and drop a file with `prefab=` into `install/BepInEx/scenariorunner/give/`. `/cursor/force` is also safe to use again; it pins a collider alongside the target, and clearing it genuinely recovers. Both are documented in the ScenarioRunner and ClientDriver READMEs.

**Two genuinely separate clients are now reachable on one Steam account.** The client rig at `TestRig/ClientRig/` runs two isolated `rocketstation.exe` instances that join the dedicated server as distinct players with distinct ClientIds and distinct `Human` bodies. Identity comes from the per-instance manifest the launcher writes, not from Steam, so no second account and no second purchase is involved. The 2026-07-30 run used it to clear the per-player merge check that had been blocked since the beginning. Operating manual: `TestRig/ClientRig/README.md` (setup, the launcher actions, the endpoint catalogue); durable internals and the traps behind them: `TestRig/ClientRig/RESEARCH.md`; shared rig rules including the session lock: `TestRig/CLAUDE.md`. This supersedes the throwaway prototype the 2026-07-30 run used, which lived in gitignored scratch.

**A listen host who paints is now reachable.** The blocker on Session A was that the rig could only drive clients against a dedicated server, and a dedicated server has no player character. A client-rig instance provisioned `-Role host` and driven with `POST /host` is now a listen host: it runs the simulation, accepts the other instance as a joiner, and plays a character of its own. Both Session A checks are therefore stageable end to end with nobody at the keyboard. **Neither has been run yet.** Sequence, refusals and what to assert on: `TestRig/ClientRig/README.md` "Hosting a world"; short rules: `TestRig/ClientRig/CLAUDE.md`; game internals: `Research/GameSystems/ListenHost.md`.

What is still out of reach, and why:

- **Session B in full.** Both instances share the one Steam session, so they report identical DLC entitlements. One owner plus one non-owner cannot be staged on this machine.

- **Console output moved onto the shared `PlayerMessage` helper (uncommitted, 2026-07-29).** Single-player is enough for all four checks; the join-summary check needs the dedicated server plus one client. Every line the mod puts in the in-game console now carries the display-name prefix `[Spray Paint Plus] ` instead of the code-name `[SprayPaintPlus] `, so the first thing to confirm is simply that the new prefix is what appears.
  - **Conflict banner (`Plugin.cs` `RepeatWarning`).** Install Color Cycler or Network Painter alongside this mod and launch. Announced in two phases now, so test both. **Phase 1, at boot:** exactly ONE red line during the splash; watch the StationeersLaunchPad boot panel and confirm it also reached `LogOutput.log`. **Phase 2, on world entry:** wait at the main menu a good 60 seconds, deliberately longer than the 25-second banner, then load a world. The six-line banner must start only AFTER the world is up, at 5-second intervals, each a single line with no stack trace under it, the sixth ending "(This warning will stop repeating; see the BepInEx log.)", then nothing. Confirm none of the six appear while still at the menu. Pause mid-banner (Escape) and confirm the rest keep coming, which is `WaitForSecondsRealtime`; plain `WaitForSeconds` would freeze on a pause. The old form was an unbounded `Debug.LogError` every 5 seconds forever, which the console re-printed lowercased in red with a full stack trace attached, and which no player could silence.
  - **First-use notice cap.** On the dedicated server set `Server - Network Painting` `Network Paint Cables` Off with the client half On, then paint a cable four times. Expected: three console lines, the third ending "No more notices about this one until you rejoin.", and silence on the fourth. The cap is unchanged code; this confirms the migration did not disturb it.
  - **Join summary.** Join that same server. Expected: exactly one console line naming every blocked function, prefixed `[Spray Paint Plus] `.
  - **Eyedropper cross-family line.** With `Cycles within paint family` in force, right-click a metallic-painted object holding a base can. Expected: the same explanation as before, once per click with no cap, and now also present in `BepInEx\LogOutput.log` at Info level, which it never used to be.
  - **Regression guard, headless.** Re-run `Scenario = spp-settings-merge-verify`. P6 asserts `LogEffectiveSettings` emits exactly one Info line on the mod's log source; nothing in this change touches that method, but it is the assertion that would catch a stray `PlayerMessage.Info` slipping onto the same source.

- **Session A: listen host plus one joined client, both driven by the client rig.** Both remaining checks require the host to hold a gun and paint, which no dedicated server can provide. The per-player merge check that used to head this list passed on 2026-07-30 against the dedicated server with two driven clients and has been removed.

  Staging, once per run: `-Provision -Role host` for `host1` and `-Role client` for `client1`, leaving `-SeedMods` on its default so each instance copies the developer's local mod set (the client rig has no `-DeployMods`; that is how this mod reaches an instance, so it has to be a current build in the developer's own mod folder). Then start the host, `-Wait -Stage menu`, `POST /host {"world":"Lunar"}`, then start the joiner and `POST /connect` at the host's game port. Confirm from the HOST that the joiner arrived (`-Status` prints `connectedClients` with the joiner's name and id) before asserting anything. Per-instance settings go through `POST /config/set` on the instance whose half you are changing, which is the point of both checks. Tear down with `-Stop -All`, which saves and orders the teardown itself. Full sequence and the refusal table: `TestRig/ClientRig/README.md` "Hosting a world".
  - **Glow, what you can do versus what you see.** Client turns `Client - Glow Paint` Off. Host glow-paints a pipe: the client must still see it glowing. Host then recolors that glowing pipe with a plain can: it must still glow for the client. A pipe that silently stops glowing for one player only is the exact defect the audit found, and this is the most valuable single observation in the session.
  - **The host's own half must not leak.** Host turns `Client - Glow Paint` Off but leaves `Server - Glow Paint` On. The client's gun must keep working normally, and the host sees the result. Before the fix the host's personal setting silently disabled glow for everyone. The host's own gun stays inert, which is what their own half asked for.

- **Session B: dedicated server, two players, one owning Metallic Paints and one not.**
  - **One owner plus one non-owner.** The non-owning player must be able to scroll to and paint with metallic colors while the owner is connected. That is vanilla shared-DLC behavior, not a bypass. The server-owns-nothing half of this is already confirmed: a single owning client joined a dedi that owns no DLC and reached all four metallic colors, with `SharedDLCManager.SharedDLC == 256` and the server logging `DLC paint map built: 16 color swatches, 16 spray can prefabs, 4 DLC-gated color(s)`.
  - **The entitlement outlives the owner.** After the owning client disconnects, metallic must stay available to everyone still connected until the world unloads. Needs a second player to remain connected and observe.
