# Equipment Plus Playtests

Implemented changes awaiting in-game confirmation. An agent records a playtest here, not in `TODO.md`, when it has changed code whose behavior can only be confirmed by running the game: single-player, a hosted multiplayer session, or the dedicated server under `DedicatedServer/`. This keeps `TODO.md` a list of work still to do, and gives one place to check whether a change already has a pending test before adding another.

Rules:
- Add an entry when code is implemented but its in-game behavior is unconfirmed. Write down everything a tester needs: what changed (commit if there is one), single-player vs multiplayer / dedicated-server, the save or world to set up, the exact in-game steps, what to watch (InspectorPlus request files, specific log lines, on-screen behavior, IC10 reads), and the expected result. Point at any staged `.work/<date>-<slug>/` request files or playbook.
- Check first. Before adding, scan the entries below so a change already covered by a pending test is not duplicated; extend the existing entry instead.
- Remove an entry when one of these happens: a run confirms it works; a run shows it broken (then add a fresh `TODO.md` item for the fix, or keep working on it now); or the player says the playtest is done. Entries are plain bullets, not checkboxes: like `TODO.md`, finished items are removed, not ticked off. Outcomes live in git history.

- **In-game console output rework (commit `2065dc72`, 2026-07-27; moved onto the shared helper 2026-07-29, uncommitted).** Everything Equipment Plus says to a player now goes through one shared helper. All cases below are single-player testable; no second player needed.
  - What changed. The mod-local `PlayerNotice` helper is gone (`PlayerNotice.cs` deleted). All three player-facing lines now call `StationeersPlus.Shared.PlayerMessage` from `Patterns/Console/PlayerMessage.cs`, linked into `EquipmentPlus.csproj` and initialised from `Awake` with `PlayerMessage.Init("Equipment Plus", Logger)`. The visible prefix therefore changed from `[EquipmentPlus]` to `[Equipment Plus]` on every line, since the helper builds the prefix from the display name. Message wording is otherwise identical to the 2026-07-27 pass. The two informational lines (helmet, tablet swap) are `PlayerMessage.Info` on `Throttle.Cooldown(5f)`: yellow, no stack trace, visible without opening the console, at most one line per 5 seconds per message. The conflict banner in `Plugin.cs` (`RepeatWarning`) is `PlayerMessage.Error` on `Throttle.Never`, still bounded by the `ConflictBannerRepeats = 6` loop at 5-second intervals, and still anchored to `Prefab.OnPrefabsLoaded` (the anchor is an open decision, see `TODO.md`). New behavior in this pass: every one of those lines is now also written to the BepInEx log and `Player.log`, and lines emitted during boot are additionally mirrored into the StationeersLaunchPad boot-log panel.
  - Mode: single-player. Any world with a helmet and an advanced tablet.
  - Case A (helmet, previously a red stack-trace block per notch): equip a helmet with no battery or a fully drained one, light off, and spin the scroll wheel hard, 15+ notches in one flick. Expect ONE yellow line "[Equipment Plus] Helmet has no power." and no stack trace, not one per notch. Wait 5 seconds, scroll again, expect a second line. Confirm the line is visible bottom-left WITHOUT pressing F3 (that is the `aged: false` behavior), then press F3 and confirm it is in the buffer too. Re-fit a charged battery and confirm the light still turns on.
  - Case B (tablet swap): fill the inventory and occupy both hands so the tablet auto-equip has nowhere to stow, then Ctrl+scroll repeatedly. Same expectation: one throttled yellow "[Equipment Plus] No room to swap..." line, no stack trace, no per-notch repeat.
  - Case C (conflict banner, only if a conflicting mod is available). This is now announced in two phases, so test both. Load with BetterAdvancedTablet or the improved_configuration mod enabled. **Phase 1, at boot:** exactly ONE red "[Equipment Plus] NOT LOADED! ..." line during the splash. Watch the StationeersLaunchPad boot panel for it, and confirm it is in `LogOutput.log`. **Phase 2, on world entry:** sit at the main menu for a good 60 seconds first, deliberately longer than the old 25-second window, then load a world. Expect the six-line banner to start AFTER the world is up, about 5 seconds apart, the last one ending "(This warning will stop repeating; see the BepInEx log.)", then silence. The whole point of this change is that waiting at the menu no longer causes the player to miss it. Also confirm the banner is not still running at the menu: the first of the six must not appear until a world is loaded. Then pause the game mid-banner (Escape) and confirm the remaining lines keep coming on schedule, which is the `WaitForSecondsRealtime` behavior; with the old `WaitForSeconds` a pause would freeze it.
  - Case D (log legs, no separate run needed): after Cases A to C, open `BepInEx\LogOutput.log` and confirm each console line appears there exactly once, at the matching severity (the two informational lines as Info, the six banner lines as Error), and that no line carries a stack trace.
  - Watch for: any doubled line, in the console or in the log. A message appearing twice would mean something still pairs `Debug.LogError` with a console call, which is the defect this pass removed. Also watch that the prefix reads "[Equipment Plus]" with the space everywhere; a stray "[EquipmentPlus]" means a call site was missed.

- **Multiplayer test checklist (deferred until a second player is online).** Two-player coverage of the already-implemented scroll-dispatch, hand-swap, lens-cycle, slot-write, and helmet-beam sync paths. Single-player re-tests of items B/C/E stay in `TODO.md` because that code is not written yet. Item A (helmet power gating) has landed, and its single-player check is Case A of the console-output entry above. This checklist is the multiplayer-only backlog.
  - Mode: multiplayer, two players (A and B).
  - Case 1: Both holding a tablet, A does Ctrl+scroll: cycles A's cartridges; B sees A's tablet update via vanilla state-sync.
  - Case 2: A has tablet in off-hand, A does Ctrl+scroll: triggers `SwapHands` (A-local; B sees no swap visualization).
  - Case 3: A has tablet in toolbelt, active hand empty, A does Ctrl+scroll: equips via `OnServer.MoveToSlot`; B observes the move.
  - Case 4: A has tablet in toolbelt, active hand has SmartStow-able item, A does Ctrl+scroll. Risk: the 1-frame yield may be insufficient on internet-latency multiplayer and false-fail the stow check; watch the log for the false fallback into the swap path.
  - Case 5: A has tablet in toolbelt, active hand item NOT SmartStow-able and NOT type-compatible with toolbelt slot, off-hand empty, A does Ctrl+scroll: 3-way swap via off-hand.
  - Case 6: Same as Case 5 but off-hand also occupied: abort with local console message "[Equipment Plus] No room to swap..."; B sees nothing. (Same wording as before, but the line is now yellow rather than red, is throttled, and carries the spaced display-name prefix; see the console-output entry above.)
  - Case 7: A wears lens, B wears different lens, A does LeftShift+scroll: A's lens cycles; B sees A's chip change via `SensorLensesSync.ActiveSensorFlag`.
  - Case 8: A scrolling while B disconnects mid-action; A's coroutine completes or fails gracefully, no NREs.
  - Case 9 (Item 7): B (remote client) clicks a writable slot logic line on a host's device; the server applies via `SetLogicSlotFromClient` and replicates back to all clients.
  - Case 10 (Item 6): B adjusts helmet beam; A sees B's beam visibly tighten/widen via `SetBeamSettingsMessage` rebroadcast.
  - Case 11 (Item 6): B adjusts beam, host saves, B disconnects, host reloads, B reconnects: B's beam restored at saved angle (host log: "Restored N helmet-beam entries from host join").
  - Mitigation if Case 4 hits the latency issue: extend the yield to multiple frames OR poll a state predicate (`yield until activeHandSlot.Get() != prevOccupant || N frames elapsed`).
