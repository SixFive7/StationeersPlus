# Network Purist Plus Playtests

Implemented changes awaiting in-game confirmation. An agent records a playtest here, not in `TODO.md`, when it has changed code whose behavior can only be confirmed by running the game: single-player, a hosted multiplayer session, or the dedicated server under `DedicatedServer/`. This keeps `TODO.md` a list of work still to do, and gives one place to check whether a change already has a pending test before adding another.

Rules:
- Add an entry when code is implemented but its in-game behavior is unconfirmed. Write down everything a tester needs: what changed (commit if there is one), single-player vs multiplayer / dedicated-server, the save or world to set up, the exact in-game steps, what to watch (InspectorPlus request files, specific log lines, on-screen behavior, IC10 reads), and the expected result. Point at any staged `.work/<date>-<slug>/` request files or playbook.
- Check first. Before adding, scan the entries below so a change already covered by a pending test is not duplicated; extend the existing entry instead.
- Remove an entry when one of these happens: a run confirms it works; a run shows it broken (then add a fresh `TODO.md` item for the fix, or keep working on it now); or the player says the playtest is done. Entries are plain bullets, not checkboxes: like `TODO.md`, finished items are removed, not ticked off. Outcomes live in git history.

- **Console-output rework for the player-facing helpers (uncommitted, 2026-07-27).** `PlayerLog` / `PlayerWarn` / `PlayerError` in `Plugin.cs` changed, plus three of their noisier callers.
  - What changed. `PlayerError` no longer calls `UnityEngine.Debug.LogError`: the console re-prints `LogType.Error` itself (it subscribes to `Application.logMessageReceivedThreaded`), so every error was being shown to the player twice, once as the controlled `PrintError` and again lowercased with a stack trace. `PlayerWarn` now prints yellow via `PrintAction` instead of red via `PrintError`, since a warning is not an error and the game has no `PrintWarning`. A new `PlayerError(string, Exception)` overload sends the full exception to the file log and only the type and message to the console. The per-piece "rebuilding ..." line in `ReplaceLongPiecesOnLoadPatch` and the per-cable align failure in `NormalizeCableRollOnLoadPatch` moved to the file log; `CableRollOnConstruct` gained a one-shot guard on its failure path to match the one already on its success path.
  - Mode: single-player first (host counts), then a hosted session if convenient. Needs a world containing long pipe or cable variants so the on-load rebuild sweep actually runs.
  - Case A, the on-load sweep: load a save with a decent number of long pieces (the more the better; a few dozen is a good stress) and watch the console during the load. Expect the summary lines only, "found N long piece(s) to rebuild..." and "done: rebuilt N ... as M single-tile segment(s)...", plus the cable-alignment summary. Previously there was also one line per long piece, each forced onto the closed-console overlay, which blanketed the screen on a large world. The per-piece detail should now appear only in `BepInEx\LogOutput.log`. Confirm the console is readable immediately after load rather than being full of this mod's output.
  - Case B, warning colour: any `PlayerWarn` line must now render YELLOW, not red. These are hard to trigger on demand (they fire on a footprint or alignment failure), so the practical check is simply that no line the mod prints is red unless it is genuinely an error. If a warning does appear, it should be yellow and carry no stack trace.
  - Case C, the build-time one-shot: place straight cables normally, including a ZoopMod drag across several cells if available. The alignment path runs on every placement. Expect NO console output at all on the normal success path. If the canonicalisation ever throws, expect exactly ONE yellow line ending "Further occurrences go to the log only.", and nothing more no matter how many cables follow.
  - Watch for: any line appearing twice in the console, which would mean a `Debug.LogError` pairing survived somewhere; and a multi-line stack trace in the console, which would mean a caller is still interpolating a bare exception instead of using the new `PlayerError(string, Exception)` overload.
  - Log-side check: the summary line's failure tail now reads "(N failed -- see the log)" rather than "see warnings above", because the per-item detail moved to the file log. Confirm the detail really is in `LogOutput.log`.
  - Also worth confirming while here, an old outstanding item from `RESEARCH.md`: no HarmonyX "Could not find type named Util.Commands.ConsoleWindow" warning at startup.
